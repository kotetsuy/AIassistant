# Phase 3 記録 — 速度比較(最終フェーズ)

- 実施日: 2026-08-13
- 結果: **完了**。3構成 × 13音源の比較表(速度 + 精度)が揃った

## 測定条件

| 項目 | 内容 |
|---|---|
| 構成 A | whisperX-ROCm `large-v3-turbo`, batch_size=8, **float16**, silero VAD |
| 構成 B | NeMo `nemotron-3.5-asr-streaming-0.6b` 一括, `ja-JP`, **float32** |
| 構成 C | 同モデルのストリーミング, `att_context_size=[56,13]`(1120ms チャンク) |
| 主指標 | **発話終了 → 転写確定**(ユーザが待たされる時間) |
| 回数 | 各構成・各音源 20 回、**中央値**。ウォームアップ 3 回 |
| 精度 | **CER**(日本語に WER は無意味)。表記ゆれを正規化してから算出 |
| 実行形態 | すべて同一プロセス内。HTTP/WS のオーバヘッドは 3 構成で同じなのでノイズにしかならない |

音源は 13 本 = 短文 9 本(1.35〜3.50秒、肉声/ずんだもん/波音リツ)+ **長文 4 本(10.44〜14.22秒、FLEURS ja_jp)**。
Phase 0 で指摘したとおり、長尺を入れないとストリーミングの利点が測れないため追加した。

計測スクリプト: `bench/bench_stt.py`(STT 単体)、`bench/bench_e2e.py`(エンドツーエンド)。
生データ: `bench/results.json` / `bench/results_e2e.json`、表: `bench/results.md`。

### CER の正規化について

Phase 0 で見つけたとおり、2 モデルは**転写内容ではなく表記の慣習**が違う。
そのまま比較すると差が誤差として乗るので、以下を正規化してから CER を出した。

| 差 | 例 |
|---|---|
| 算用数字 / 漢数字 | whisperX「2番目」 vs NeMo「二番目」 |
| 文末句読点 | whisperX は「。」「、」を付ける、NeMo は付けないことが多い |
| 全角半角 | NFKC 正規化 |

## 結果 1 — 発話終了 → 転写確定(主指標)

| 音源 | 長さ | A: whisperX | B: NeMo一括 | C: NeMoストリーミング |
|---|---|---|---|---|
| ritsu_greeting | 0.85s | 254ms | 81ms | **102ms** |
| zundamon_greeting | 1.06s | 254ms | 84ms | **48ms** |
| ritsu_river | 1.91s | 283ms | 95ms | **101ms** |
| ritsu_mountain | 2.15s | 292ms | 113ms | **106ms** |
| zundamon_river | 2.31s | 284ms | 112ms | **50ms** |
| zundamon_mountain | 2.45s | 291ms | 112ms | **52ms** |
| human_greeting | 3.25s | 258ms | 108ms | **103ms** |
| human_mountain | 3.50s | 293ms | 117ms | **49ms** |
| human_river | 3.50s | 287ms | 119ms | **49ms** |
| long1 | 10.44s | 432ms | 221ms | **53ms** |
| long4 | 12.54s | 461ms | 261ms | **49ms** |
| long3 | 12.84s | 545ms | 274ms | **50ms** |
| long2 | 14.22s | 460ms | 255ms | **95ms** |

読み取れること:

1. **NeMo 一括は whisperX の約 2〜3 倍速い**(短文 254〜293ms → 81〜119ms、長文 432〜545ms → 221〜274ms)
2. **ストリーミングの確定時間は音声長にほぼ依存しない**(48〜106ms)。
   発話終了時点で未処理なのは最後のチャンク分だけだから
3. したがって **発話が長いほど差が開く**。3.5秒で whisperX 比 5.8倍、12.8秒で 10.8倍
4. **短文ではストリーミングが一括に負けることがある**(`ritsu_greeting` 102ms vs 81ms)。
   1秒未満の発話だと一括でも十分速く、ストリーミングは終端処理のオーバヘッドが相対的に効く
5. C の値が 48〜106ms とばらつくのは、**発話終端がチャンク境界のどこに落ちるか**で
   未処理分が 0〜1120ms 変わるため。構造的なばらつきで、実行ごとのブレではない

## 結果 2 — 精度(CER、正規化後)

| 音源 | A: whisperX | B: NeMo一括 | C: NeMoストリーミング |
|---|---|---|---|
| 短文 9 本すべて | **0.0%** | **0.0%** | **0.0%** |
| long1 (10.44s) | **0.0%** | 2.2% | 2.2% |
| long2 (14.22s) | **0.0%** | 2.2% | 2.2% |
| long3 (12.84s) | **9.9%** | 21.1% | 21.1% |
| long4 (12.54s) | 17.9% | 17.9% | 17.9% |

**B と C の CER は全音源で完全に一致した。** ストリーミング化による精度低下は無い。

一方で **長文では whisperX の方が正確**:

- `long1`: NeMo は「敵**対**的」→「敵**体**的」
- `long2`: NeMo は「聖**域**神社」→「**成**域神社」
- `long3`: 固有名詞が多い文(バルセロナ / カタルーニャ語)で差が大きい。
  whisperX 9.9% に対し NeMo 21.1%。NeMo は「公用**語**」→「公用**後**」、「スペイン語です」→「スペイン**ゴリス**」など崩れる
- `long4`: 両方 17.9% で引き分け(どちらも難しい)

**短い会話文では両者とも完璧で、差は長く複雑な読み上げ文でのみ出る。**
0.6B と large-v3-turbo のモデルサイズ差が、そのまま語彙・固有名詞の弱さとして出ていると読める。

## 結果 3 — エンドツーエンド(発話終了 → 最初の音声が鳴るまで)

`bench/bench_e2e.py`。three-vrm の WS を購読し、最初の `speak` チャンクが届くまでを計測。
**human_river (3.50s) で各 30 回。**

:::note
初回の計測では **whisperX の基準線が抜けていた**(NeMo の一括 vs ストリーミングしか測っていなかった)。
移行前後の比較にならないので、`bench_e2e.py` に `--label` と `--no-stream` を追加して測り直した。
whisperX はストリーミング非対応なので、`--no-stream` を付けないと来ない音声を待って
タイムアウトする。
:::

| 構成 | 中央値 | 範囲 | 1秒超 |
|---|---|---|---|
| **whisperX 一括**(移行前) | 895ms | 608-1099ms | **11/30 (37%)** |
| **NeMo 一括**(移行後の既定) | **735ms** | 415-939ms | **0/30** |
| NeMo ストリーミング | **614ms** | 353-903ms | **0/30** |

中央値では約 160ms の短縮。ただし**効いているのは分布の方**で、
whisperX では約 4 割の発話が 1 秒を超えていたのが、NeMo では 30 回とも 1 秒未満になった。

### この指標はセッションごとにぶれる

whisperX の中央値を別々のセッションで 3 回測ったところ **895 / 937 / 1074 ms** と割れた
(いずれも 15〜30 回の中央値)。**単発の中央値を根拠にしてはいけない。**

対して「1 秒を超える割合」は 37〜60% とどのセッションでも一貫して高い。
**この指標は分布の形で語る方が頑健**である。

NeMo 側は 713 / 723 / 735 ms と安定していた。STT の処理時間自体が短いぶん、
ばらつきの発生源である LLM 側の影響を相対的に受けにくいと読める。

ぶれる理由は、この区間に「LLM が最初の一文を生成する時間 + VOICEVOX がそれを合成する時間」が
含まれ、**LLM の生成内容が実行ごとに変わる**ため。最初の文が長ければ合成にも時間がかかる。

### ストリーミングの効果は短文では限定的

614ms と最速だが、一括との差は約 120ms にとどまる。3.5 秒の発話では
STT 単体の差が 70ms(119ms → 49ms)しかなく、**LLM のばらつきに大部分が埋もれる**。
ストリーミングが効くのは STT 側の差が開く長い発話。

## 結論と既定バックエンドの判断

**既定は NeMo のままでよい。** 根拠:

- 実際の用途である**短い会話文では、精度は whisperX と同じ(両方 CER 0%)**で、速度は 2〜3 倍
- ストリーミングを使えば発話長によらず **50〜100ms** で確定する
- whisperX はフォールバックとして同居しているので、精度が要る場面では
  `STT_BACKEND=whisperx` で即座に切り替えられる

**ただし以下は認識しておくべき制約:**

1. **長く複雑な発話では whisperX の方が正確**(long3 で CER 9.9% vs 21.1%)。
   固有名詞や専門語が多い用途なら既定を見直す価値がある
2. **エンドツーエンドの体感改善は STT の数字ほどではない**。LLM と TTS が支配的
3. 1 秒未満の発話ではストリーミングが一括に負ける。ただし差は 20ms 程度で実害は無い
